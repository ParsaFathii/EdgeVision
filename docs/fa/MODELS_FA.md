# مدل‌ها

این سند رجیستری مدل‌های اج‌ویژن را توضیح می‌دهد: چیست، چه چیزی در آن هست و — مهم‌تر از آن — تشخیص در این نسخه واقعاً چگونه انجام می‌شود.

## رجیستری یعنی چه

جدول `models` در دیتابیس، **فرادادهٔ پیکربندی مدل‌های قابل استقرار** را نگه می‌دارد: نام، نوع وظیفه، قالب، دستگاه، شکل ورودی، فهرست کلاس‌ها، حجم، مجوز و توضیح. هیچ فایل وزنی به آن وصل نیست و هیچ مسیری برای بارگذاری وزن وجود ندارد. رجیستری جایی است که مشخص می‌کند «اگر مدل X استقرار یابد، با چه پیکربندی باید اجرا شود» — قراردادی که داشبورد، API و مستندات حولش هم‌راستا می‌مانند.

سرویس موتور موقع هر بوت، دو رکورد را به‌صورت خودکار و idempotent (با `INSERT OR IGNORE` روی کلید نام) seed می‌کند؛ پس رکوردهای رجیستری همیشه موجودند حتی بعد از پاک‌کردن دستی.

## دو پیکربندی seed شده

| فیلد | edgevision-detect-s | edgevision-detect-m |
|---|---|---|
| نوع وظیفه | OBJECT_DETECTION | OBJECT_DETECTION |
| قالب / دستگاه | ONNX / CPU | ONNX / CPU |
| شکل ورودی | 1x3x416x416 | 1x3x640x640 |
| کلاس‌ها | PEDESTRIAN، VEHICLE، CYCLIST | PEDESTRIAN، VEHICLE، CYCLIST |
| حجم اعلامی | ۷٬۵۸۰٬۰۰۰ بایت (~۷٫۲ مگابایت) | ۲۵٬۹۰۰٬۰۰۰ بایت (~۲۴٫۷ مگابایت) |
| مجوز | Apache-2.0 | Apache-2.0 |
| وضعیت | فعال | غیرفعال |

می‌توانید با `POST /api/v1/models` پیکربندی دیگری ثبت کنید (شرح کامل فیلدها در [API_FA.md](API_FA.md)). مثال:

```bash
curl -s -X POST http://localhost:3000/api/v1/models \
  -H "content-type: application/json" \
  -d '{
        "name": "edgevision-detect-l",
        "task": "OBJECT_DETECTION",
        "format": "ONNX",
        "device": "CPU",
        "inputShape": "1x3x800x800",
        "classesJson": ["PEDESTRIAN", "VEHICLE", "CYCLIST"],
        "sizeBytes": 52000000,
        "license": "Apache-2.0",
        "description": "پیکربندی بزرگ‌تر برای سخت‌افزار قوی‌تر"
      }'
```

محدودیت‌های ثبت: نام یکتا و ۱ تا ۸۰ نویسه، `inputShape` الزامی و حداکثر ۴۰ نویسه، `classesJson` آرایه‌ای بین ۱ تا ۲۰ رشتهٔ حداکثر ۴۰ نویسه‌ای. ثبت یک پیکربندی **هیچ چیزی نصب یا اجرا نمی‌کند**؛ فقط یک ردیف فراداده اضافه می‌شود که بعداً در استقرار واقعی مدل مرجع خواهد بود.

## معنای تک‌فعال

مدل فعال تنها یک تاست و این قید در تراکنش اعمال می‌شود: فعال‌کردن یک مدل، در همان لحظه `isActive` همهٔ مدل‌های دیگر را صفر می‌کند و بعد مدل هدف را یک. یعنی هرگز دو مدل «فعال» نمی‌بینید و کلاینت‌ها لازم نیست قفل‌گذاری کنند. خاموش‌کردن مدل فعال، رجیستری را بدون مدل فعال رها می‌کند — که در این نسخه هیچ جریمه‌ای ندارد، چون استنتاج از رجیستری عبور نمی‌کند.

## تشخیص در این نسخه واقعاً چگونه انجام می‌شود

صریح بگوییم: **تشخیص را آشکارساز شبکه‌ای موتور بومی انجام می‌دهد، نه یک مدل ONNX.** جریان کار هر فریم این است:

1. پوشش اشیای رندرشده روی شبکهٔ `gridCols×gridRows` با ۲۰ کانال هستهٔ چندمقیاسی محاسبه می‌شود — هزینهٔ واقعی و متناسب با ابعاد شبکه
2. سلول‌های بالای آستانهٔ occupancy با مؤلفه‌های همبند خوشه می‌شوند
3. جعبهٔ هر خوشه با اکتشافی اندازه/نسبت طبقه‌بندی می‌شود (خودرو/دوچرخه‌سوار/عابر پیاده)
4. اطمینان از ثبات پوشش، منطقی‌بودن سطح و تیزی پاسخ ساخته می‌شود

این یک جانشین قطعی و آگاهانه برای گام استنتاج ONNX است تا کل خط‌لوله (صف، ردیاب، رویدادها، سنجه‌ها) با بار واقعی و قابل‌اندازه‌گیری قابل توسعه و آزمون باشد. جزئیات در [ARCHITECTURE_FA.md](ARCHITECTURE_FA.md).

## مسیر یکپارچه‌سازی آیندهٔ ONNX

اگر روزی مدل ONNX جای آشکارساز شبکه‌ای را بگیرد، نقاط اتصال از قبل روشن‌اند و همه در یک ماژول‌اند:

- `engine-cpp/src/detector.hpp` / `detector.cpp` — کل مرز «فریم وارد، تشخیص خارج»؛ ساختار `Detection` و امضای `detect()` همان قراردادی است که یک runtime استنتاج هم باید پر کند
- `set_grid()` — تبدیل به پارامتر ورودی مدل (رزولوشن استنتاج)
- `set_output_filter()` — آستانهٔ اطمینان و فیلتر کلاس، مستقل از سازوکار استنتاج
- ساختارهای `SceneObject` ورودی — معادل تانسور پیش‌پردازش‌شدهٔ ورودی

چون خروجی آشکارساز همان شکلی را می‌دهد که ردیاب و پروتکل NDJSON انتظار دارند، جایگزینی فقط درون این ماژول می‌ماند و هیچ لایهٔ دیگری تغییر نمی‌کند.

## هیچ فایل وزنی توزیع نمی‌شود

مخزن اج‌ویژن هیچ وزن مدل‌ای ندارد و نداشتنش یک قاعدهٔ بهداشتی است، نه فراموشی:

- مدل‌های YOLO در نسخه‌های مختلف با مجوزهای AGPL-3.0 یا GPL-3.0 منتشر می‌شوند که با توزیع در یک مخزن Apache-2.0 ناسازگارند
- پس **فایل‌های وزنی AGPL/GPL هرگز نباید کامیت شوند** — نه در مخزن، نه در پوشه‌های fixtures یا assets
- اگر مدل واقعی می‌خواهید، خودتان جداگانه دانلودش کنید و پیش از هر استفادهٔ واقعی، مجوز آن نسخه را جداگانه بررسی کنید؛ رجیستری فقط فراداده را ثبت می‌کند و محلی برای مسیر فایل هم ندارد

## فیلدهای رجیستری

| فیلد | معنا |
|---|---|
| name | نام یکتای پیکربندی (کلید idempotent سید) |
| task | نوع وظیفه؛ در هر دو رکورد seed `OBJECT_DETECTION` |
| format / device | قالب اجرا و دستگاه هدف (ONNX / CPU) |
| inputShape | شکل تانسور ورودی به‌شکل متنی |
| classesJson | فهرست کلاس‌هایی که پیکربندی پشتیبانی می‌کند |
| sizeBytes | حجم اعلامی فایل وزن مربوط (فراداده؛ فایل موجود نیست) |
| license | مجوز فایل وزنی مربوط — برای بررسی بهداشت حقوقی |
| description | توضیح فارسی برای نمایش در داشبورد |
| isActive | تنها یک رکورد می‌تواند true باشد (ترانشی) |

## پرسش‌های رایج

**اگر مدل فعال را خاموش کنم، تشخیص متوقف می‌شود؟**
نه. استنتاج از رجیستری عبور نمی‌کند؛ خاموش‌کردن مدل فقط یک پرچم فراداده را برمی‌گرداند و خط‌لوله همان‌طور می‌چرخد.

**پس فعال‌کردن مدل چه اثری دارد؟**
در این نسخه فقط یک نشانهٔ پیکربندی است — برای این‌که ابزارها و مستندات بدانند کدام پیکربندی مرجع است. اثر اجرایی روی بار پردازش ندارد.

**چرا inputShape مدل (مثلاً ۴۱۶×۴۱۶) با شبکهٔ استریم (مثلاً ۴۰×۲۴) فرق دارد؟**
دو چیز متفاوت‌اند: `inputShape` پیکربندی مدلِ آینده است؛ `gridCols/gridRows` استریم، شبکهٔ آشکارساز جانشین است که امروز واقعاً کار می‌کند. بزرگ‌کردن دومی تأخیر را واقعاً بالا می‌برد؛ اولی فعلاً فراداده است.
