# معماری

این سند نگاه مهندسی به اج‌ویژن است: چه چیزی کجا اجرا می‌شود، مرزها کدام‌اند و هر تصمیم طراحی چرا گرفته شده. نمودار کلی در [../assets/architecture.svg](../assets/architecture.svg)، جریان داده در [../assets/data-flow.svg](../assets/data-flow.svg) و خط‌لولهٔ بلادرنگ در [../assets/realtime-pipeline.svg](../assets/realtime-pipeline.svg) آمده است.

## چهار لایه

| لایه | فرایند | مسئولیت |
|---|---|---|
| موتور بومی (`engine-cpp/`) | یک فرایند به‌ازای هر نشست | تولید صحنه، تشخیص، ردیابی، رویدادها، سنجه‌ها |
| سرویس موتور (`mini-services/engine-service/`، پورت ۳۰۰۳) | یک فرایند | راه‌اندازی/مراقبت فرایندهای موتور، تنها نویسندهٔ دیتابیس، انتشار زنده |
| API وب (`src/app/api/v1/`، پورت ۳۰۰۰) | فرایند اپ Next.js | خواندن مستقیم، نوشتن با اعتبارسنجی و هدایت |
| داشبورد (`src/`، همان فرایند اپ) | مرورگر | رابط فارسی RTL، صحنهٔ زندهٔ SVG، نمودارها |

یک SQLite واحد (`db/custom.db`) لایه‌ها را به هم می‌دوزد.

## موتور بومی

### مدل فرایند و رشته

موتور به‌ازای هر نشست استریم یک فرایند جداگانه است؛ اگر یکی از استریم‌ها خراب شود، بقیهٔ سیستم سالم می‌ماند. داخل هر فرایند دو رشته است:

- **رشتهٔ تولیدکننده:** صحنه را با گام ثابت `dt = 1/targetFps` جلو می‌برد، یک `Frame` (شمارندهٔ ترتیبی + زمان epoch + وضعیت اشیا) می‌سازد و در صف می‌گذارد. خواب‌ها در برش‌های حداکثر ۱۰۰ میلی‌ثانیه‌اند تا توقف هرگز معطل نماند و بعد از ایستگاه‌های ناخواسته «جبران انفجاری» نمی‌کند.
- **رشتهٔ مصرف‌کننده:** فریم را از صف برمی‌دارد و کل خط‌لوله را روی آن اجرا می‌کند: آشکارساز → ردیاب → موتور رویداد → انتشار خروجی. بین فریم‌ها stdin را هم به‌صورت non-blocking می‌خواند (فرمان‌ها هرگز خط‌لوله را نمی‌بلکنند).

بین این دو یک **صف محدود** است (`queueCapacity`، پیش‌فرض ۳۰). سیاستش «دورریختن قدیمی‌ترین» است: وقتی صف پر شود، قدیمی‌ترین فریم حذف و شمارده می‌شود، نه اینکه تولیدکننده بلاک شود یا فریم تازه دور ریخته شود. منطقش ساده است — در تحلیل زنده، فریم کهنه وقتی مصرف‌کننده عقب افتاده ارزشی ندارد؛ وضعیت الان مهم است. شمارندهٔ `droppedTotal` این سیاست را شفاف نگه می‌دارد.

### مرز پروتکل NDJSON

موتور روی **stdout** خط‌های JSON سخت‌گیرانه (یک آبجکت در هر خط) می‌نویسد و روی **stdin** فرمان متنی می‌پذیرد: `stop`، `ping`، `set grid CxR`، `set queue N`، `set emit-stride N`. انواع خطوط خروجی: `ready`، `session_started`، `state`، `frame`، `event`، `metrics`، `settings_applied`، `pong`، `session_stopped`، `error`.

چرا stdout/stdin و نه مثلاً کتابخانهٔ سوکت؟

- **مرز مستقل از زبان:** هر فرایندی که بتواند فرایند spawn کند و خروجی‌اش را بخواند می‌تواند موتور را به کار بگیرد — سرویس Bun امروز، یک اسکریپت تست پایتون فردا.
- **ایزوله‌کردن کرش:** موتور اگر کلاً از پا دربیاید، فقط فرایند خودش است؛ سرویس خروج غیرصفر را می‌بیند و نشست را صادقانه ERROR می‌کند. هیچ حالت اشتراکی‌ای بین دو فرایند نیست که خراب شود.
- **stderr جدا است:** لاگ‌های تشخیصی موتور به stderr می‌روند و هرگز با پروتکل قاطی نمی‌شوند.

خروج فرایند معنادار است: `0` پایان موفق، `2` خطای پیکربندی (با خط `CONFIG_INVALID`)، `3` خطای داخلی. SIGTERM و SIGINT هر دو به توقف تمیز می‌رسند؛ SIGPIPE نادیده گرفته می‌شود تا بسته‌شدن لولهٔ خروجی به‌شکل خطای write مدیریت شود نه سیگنال.

#### آرگومان‌های خط فرمان موتور

سرویس موتور این‌ها را از رکورد استریم می‌سازد و به فرایند spawn می‌دهد:

| آرگومان | از کجا | بازه |
|---|---|---|
| `--session-id` / `--stream-id` | شناسه‌های UUID تولیدی سرویس | — |
| `--seed` | هش FNV-1a قطعی از شناسهٔ استریم | — |
| `--scene` | ستون scene استریم | STREET/INTERSECTION/PARKING |
| `--width` / `--height` | پیکربندی استریم | ۳۲۰–۱۹۲۰ / ۲۴۰–۱۰۸۰ |
| `--target-fps` | پیکربندی استریم | ۱–۳۰ |
| `--objects` | objectCount | ۳–۲۰ |
| `--queue-capacity` | queueCapacity | ۵–۲۰۰ |
| `--confidence` | confidenceThreshold | ۰٫۰۵–۰٫۹۵ |
| `--class-filter` | classFilter (اگر غیرخالی) | فهرست با کاما |
| `--roi` / `--line` | roiJson / lineJson (اگر تعریف شده) | چهار عدد نرمال‌شده |
| `--grid` | gridCols×gridRows | ۱۶–۸۰ در ۹–۴۸ |

`--seed` قطعی از شناسهٔ استریم درمی‌آید، پس هر استریم همیشه همان دنبالهٔ حرکت‌ها را بازتولید می‌کند — شرط تکرارپذیری آزمون‌ها.

#### نمونهٔ واقعی خطوط پروتکل

و یک بدنهٔ اعتبارسنجی خراب، خروج تمیز می‌گیرد:

### آشکارساز

گام «استنتاج» یک آشکارساز شبکه‌ای قطعی است — جانشین آگاهانهٔ مدل ONNX در این نسخه:

1. **کوانتیزه‌کردن:** پوشش هر شیء روی شبکهٔ `cols×rows` با ۲۰ کانال هستهٔ چندمقیاسی (۴ کانال ریز برای occupancy و کانال‌های درشت برای ویژگی تیزی) محاسبه می‌شود. این جست‌وجو عمداً کامل است — هزینهٔ هر فریم واقعاً متناسب با ابعاد شبکه است و همین چیزی است که تأخیر اندازه می‌گیرد.
2. **آستانه و مؤلفه‌های همبند:** سلول‌ها با پاسخ ریز بالای ۰٫۵ «اشغال» می‌شوند و با union-find چهارتجاورتی خوشه می‌شوند (خوشه‌های تک‌سلولی نویزه حساب می‌شوند).
3. **جعبه و طبقه‌بندی:** جعبهٔ هر خوشه از لبه‌های سلول‌ها درمی‌آید (لبهٔ سلول‌ها منبع اصلی خطاست) و با اکتشافی اندازه/نسبت کلاس می‌گیرد: عرض بزرگ خودرو، متعادل دوچرخه‌سوار، باریک عابر پیاده. اشیای هم‌پوشان در یک خوشه ادغام می‌شوند — یعنی occlusion سنگین واقعاً کیفیت تشخیص را پایین می‌آورد.
4. **اطمینان:** ترکیب ثبات پوشش نسبت به فریم قبل، منطقی‌بودن سطح جعبه، تیزی پاسخ و یک نوفهٔ قطعیِ محدود؛ نتیجه در بازهٔ ۰٫۲ تا ۰٫۹۹.

آشکارساز فقط «ردپای رندرشده» را می‌بیند — هرگز شناسه یا کلاس ground-truth صحنه را. فیلتر کلاس و آستانهٔ اطمینان همین‌جا اعمال می‌شود تا ردیاب فقط همان چیزی را ببیند که پروتکل منتشر می‌کند.

### ردیاب

ردیاب نزدیک‌ترین‌همسایهٔ IoU است بدون مدل حرکت (خانوادهٔ SORT). پارامترهای ثابت: `minHits ۳`، `maxAge ۱۲`، `minIoU ۰٫۳`.

چرخهٔ حیات مسیر: تشخیص‌های جفت‌نشده مسیر آزمایشی می‌سازند؛ بعد از ۳ برخورد **متوالی** مسیر «تأییدشده» می‌شود و فقط همین‌ها منتشر می‌شوند؛ بعد از ۱۲ فریم بدون برخورد مسیر حذف می‌شود. جفت‌شدن حریصانه است (بیشترین IoU اول) و مرتب‌سازیش قطعی است تا خروجی بین اجراها تکرارپذیر بماند. «الان جفت شده» و «فریم قبل جفت شده» به‌صراحت از هم جدا می‌شوند — مسیر دیده‌شده در فریم قبل ولی نادیده در الان، منتشر نمی‌شود.

### هندسهٔ رویدادها

- **عبور از خط:** سمت علامت‌دار مرکز مسیر نسبت به خط جهت‌دار (حاصل‌ضرب برداری دوبعدی). رویداد فقط وقتی صادر می‌شود که علامت از یک سمت معتبر به سمت معتبر دیگر برگردد — یک‌بار در هر گذر، نه در هر فریم. جهت از محور غالب حرکت نسبت به جهت خط درمی‌آید (L2R/R2L برای خط عمودی، T2B/B2T برای افقی).
- **ورود/خروج ناحیه:** مرکز باید ۰٫۰۲ (نرمال‌شده) **داخل** مستطیل برود تا ورود بگیرد و ۰٫۰۲ **بیرون** برود تا خروج. این هیسترزیس عمداً هست تا مرکزی که لبهٔ ناحیه نوسان می‌کند، رویداد اسپم نسازد.
- تولد مسیر داخل ناحیه یا روی یک سمت خط، ساکت مقداردهی می‌شود — چیزی که «مشاهده نشده» رویداد ندارد.

### تعریف دقیق سنجه‌ها

همه از پنجرهٔ لغزان ۲ ثانیه (حداکثر ۵۱۲ نمونه) واقعی‌اند:

- **sourceFps / processedFps:** شمارش واقعی رخدادهای تولید/پردازش تقسیم بر طول زمانی پنجره — نه ساعتی که کسی تنظیم کرده.
- **تأخیر هر فریم:** زمان `steady_clock` دور «تشخیص + ردیابی + رویدادها + شروع سریال‌سازی» همان فریم. در خط `frame` به‌عنوان `latencyMs` و در تیک سنجه‌ها به‌صورت avg/min/max/P50/P95 پنجره.
- **cpuPercent:** اختلاف utime+stime فرایند (از `/proc/self/stat`) بین دو تیک متوالی تقسیم بر زمان دیواری.
- **memoryMb:** `VmRSS` از `/proc/self/status`.

### وضعیت DEGRADED

با هیسترزیس: اگر `processedFps < 0.6 × sourceFps` به‌مدت ۵ ثانیه (بعد از ۲ ثانیه گرم‌شدن) بماند، موتور خط `state: DEGRADED` می‌فرستد؛ برای برگشتن به RUNNING باید ۱۰ ثانیه پیوسته بالای آستانه بماند. به این ترتیب یک لرزش لحظه‌ای وضعیت را عوض نمی‌کند.

## سرویس موتور

سرویس (Bun + TypeScript) تمام نوشتن‌های دیتابیس را در انحصار دارد:

- **راه‌اندازی نشست:** برای شروع استریم یک فرایند موتور با آرگومان‌های کامل (session-id، seed قطعی مشتق از شناسهٔ استریم، صحنه، ابعاد، شبکه، صف، آستانه، ROI و خط) spawn می‌کند، رکورد نشست با STARTING می‌سازد و حداکثر ۲٫۵ ثانیه برای تایید RUNNING صبر می‌کند. استریم همزمان ۴۰۹ می‌گیرد.
- **توقف پلکانی:** فرمان `stop` روی stdin → ۵ ثانیه مهلت → SIGTERM → ۲ ثانیه مهلت → SIGKILL. خلاصهٔ نهایی (`session_stopped`) رکورد نشست را کامل می‌کند. دلیل پایان (`reason`) همیشه ثبت می‌شود: `user_stop`، `signal`، `eof` یا `engine_crash_exit_*`.
- **دسته‌ای‌کردن:** تشخیص‌ها هر ۱ ثانیه در یک تراکنش flush می‌شوند؛ رویدادها بی‌درنگ ثبت می‌شوند؛ از هر ۲ خط سنجه، یکی در دیتابیس می‌رود.
- **پاک‌سازی:** هر ۵ دقیقه — سنجه‌های قدیمی‌تر از ۲۴ ساعت، تشخیص‌ها به سقف ۱۰۰ هزار ردیف و رویدادها به سقف ۲۰ هزار ردیف هرس می‌شوند (قدیمی‌ترین‌ها اول).
- **صادق بودن موقع کرش:** بوت سرویس نشست‌های یتیم (از hot-reload یا کرش قبلی) را با `ERROR/service_restarted` می‌بندد؛ خروج غیرصفر موتور با دلیل واقعی (`engine_crash_exit_*`) ثبت می‌شود.

دیتابیس با `bun:sqlite` در حالت **WAL** و `busy_timeout=5000` باز می‌شود تا خوانندهٔ Prisma در فرایند اپ بدون قفل‌شدن با این نویسنده کنار بیاید.

### اتاق‌های socket.io

هر اتصال سوکت موقع وصل شدن پیام `hello` می‌گیرد. عضویت با `subscribe {streams:[...]}` انجام می‌شود و سوکت به اتاق `stream:<id>` می‌پیوندد؛ همهٔ پیام‌های زنده (frame، metrics، event، session) فقط به همان اتاق می‌روند — کلاینت‌هایی که subscribe نکرده‌اند چیزی نمی‌گیرند. مسیر socket.io روی `/` است (قرارداد گیت‌وی). پینگ سوکت هر ۲۵ ثانیه و مهلتش ۶۰ ثانیه است.

## API وب: تفکیک خواندن/نوشتن

نقاط خواندنی (`GET`ها) مستقیماً با Prisma از SQLite می‌خوانند — مسیر کوتاه، بدون پرش اضافی. نقاط تغییردهنده اول با zod اعتبارسنجی می‌شوند، بعد به API داخلی سرویس موتور (`/internal/*` روی پورت ۳۰۰۳، محافظ با توکن `x-internal-token`) هدایت می‌شوند و پاسخ را دوباره از دیتابیس می‌خوانند.

چرا؟ چون نوشتنِ دو جا (Prisma در اپ و سرویس) هم‌زمان روی یک SQLite یعنی ریسک واقعی ناسازگاری و قفل؛ یک نویسندهٔ واحد این کلاس باگ را کلاً حذف می‌کند و اعتبارسنجی دو لایه‌ای (اپ + سرویس) خطاها را فارسی و دقیق نگه می‌دارد. مهلت‌ها هم متفاوت‌اند: شروع ۱۰ ثانیه (spawn و RUNNING شدن موتور)، توقف ۱۵ ثانیه (تا پلکانی SIGKILL تمام شود).

## توالی جریان داده

1. رشتهٔ تولیدکنندهٔ موتور فریم می‌سازد → صف محدود
2. رشتهٔ مصرف‌کننده: تشخیص → ردیابی → رویدادها → خط NDJSON
3. سرویس خط را می‌خواند: تشخیص‌ها به بافر، رویداد بی‌درنگ INSERT، سنجه‌ها هر دومینی persist
4. سرویس همان لحظه به اتاق `stream:<id>` broadcast می‌کند
5. مرورگر پیام را می‌گیرد: صحنهٔ SVG، کارت‌های متریک، فید رویداد به‌روز می‌شوند
6. درخواست‌های بعدی داشبورد (کاوشگر، تحلیل‌ها) از همان دادهٔ ذخیره‌شده می‌خوانند

## مرزهای امنیتی

- **توکن داخلی:** API داخلی سرویس (پورت ۳۰۰۳) فقط با هدر `x-internal-token` جواب می‌دهد (پیش‌فرض `edgevision-local`، قابل تغییر با `EV_INTERNAL_TOKEN`). این یک راز محلی است، نه احراز هویت چندکاربره.
- **محدودیت نرخ:** ۶۰ درخواست تغییردهنده در دقیقه به‌ازای هر IP (سطل توکن در حافظه)؛ بیشترش پاسخ ۴۲۹ فارسی می‌گیرد.
- **سقف بدنه:** ۱ مگابایت روی API عمومی و ۲۵۶ کیلوبایت روی API داخلی؛ بیشترش ۴۱۳.
- **بدون نشت جزئیات:** استثناهای مدیریت‌نشده به پیام عمومی «خطای داخلی سرور» ختم می‌شوند؛ stack trace هرگز به کلاینت نمی‌رسد.
- **شناسه‌های موتور پاک‌سازی می‌شوند** پیش از آنکه در JSON سرریز کنند.
- **احراز هویت عمداً خارج از نسخه ۱٫۰٫۰ است** (استقرار تک‌کاربره)؛ شرح کامل در SECURITY.md.
